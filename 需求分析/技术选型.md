# 技术选型


### Android端

1. 开发语言：Java
   - **选择原因**：技术栈稳定成熟，与Android SDK原生集成度最高，团队学习成本和项目风险低。
   - **优势**：
       - **生态稳定**：海量教程、社区支持和第三方库，遇坑易填。 
       - **工具链支持完善**：Android Studio对其编译、调试和分析工具的支持已达极致。
       - **团队协作成本低**：对于以Java为主的团队，无需额外的语言学习与转型。
    - **不足**：
       - **语言现代性不足**：相比Kotlin，代码更冗长，缺少空安全、扩展函数等特性，可能导致更多的样板代码和潜在的空指针异常。
   - **挑战与解决**：
       - **挑战**：在复杂业务逻辑下，代码可维护性和开发效率可能低于Kotlin。
       - **解决思路**：制定严格的代码规范（如使用`@Nullable`/`@NonNull`），并利用Lint工具进行静态检查。在长期规划中，可考虑向Kotlin渐进式迁移。

2. 网络层：Retrofit + OkHttp
   - **选择原因**：行业标准，提供类型安全、声明式的API定义，极大提升网络层开发效率和可维护性。
   - **优势**：
       - **高效简洁**：通过注解配置API，自动生成实现代码。
       - **灵活强大**：通过OkHttp拦截器可统一处理认证、日志、缓存和重试逻辑。
       - **与异步框架友好**：可轻松适配RxJava或协程，处理线程切换。
   - **不足**：
       - **接口定义集中**：所有API接口集中管理，在超大型项目中可能变得臃肿（可通过模块化解决）。
   - **挑战与解决**：
       - **挑战**：多风控数据源（如征信、反欺诈、行为分析）的统一管理和错误处理。
       - **解决思路**：利用拦截器实现全局的请求签名、Token管理和错误码统一转换。为不同数据源创建不同的Retrofit实例，实现隔离与灵活配置。

3. 本地数据：Room
   - **选择原因**：Android Jetpack官方组件，为SQLite提供抽象层，保证类型安全和高性能。
   - **优势**：
       - **编译时校验**：SQL查询在编译时即被验证，杜绝运行时错误。
       - **与架构组件无缝集成**：查询结果可轻松暴露为`LiveData`，实现数据驱动UI。
       - **减少模板代码**：免去手动处理`Cursor`和`SQLiteOpenHelper`的繁琐。
   - **不足**：
       - **学习曲线**：需要理解`Entity`, `DAO`, `Database`三个核心概念及其关系。
   - **挑战与解决**：
       - **挑战**：敏感用户数据和风控规则的本地安全存储。
       - **解决思路**：集成**SQLCipher**等加密库对数据库文件进行加密。结合Android Keystore系统管理加密密钥。

4. 状态管理：ViewModel + LiveData
   - **选择原因**：Android官方推荐的架构组件，专为UI状态管理设计，具备生命周期感知能力。
   - **优势**：
        - **生命周期安全**：避免因屏幕旋转等配置变更导致数据丢失，以及内存泄漏。
        - **数据与UI解耦**：UI（Activity/Fragment）仅负责显示，业务逻辑和数据保存在ViewModel中。
        - **测试友好**：ViewModel可独立于UI进行单元测试。
   - **不足**：
        - **数据流处理能力有限**：`LiveData`功能相对简单，对于复杂的响应式数据变换、组合（如合并多个数据源）显得力不从心。
   - **挑战与解决**：
        - **挑战**：管理风控申请多步骤表单的复杂状态，以及来自多个数据源（网络、数据库）的异步状态同步。
        - **解决思路**：
           在ViewModel内使用**状态封装**，定义一个包含所有UI状态的`Data Class`。
           对于简单场景，`LiveData`足够；若业务极其复杂，可考虑引入**Kotlin Flow**（即使主语言是Java，ViewModel层也可用Kotlin编写）来替代`LiveData`，以获得更强大的流处理能力。

5. 图片加载：Glide
    - **选择原因**：功能全面、性能优化极致、社区活跃的图片加载库。
    - **优势**：
        - **生命周期感知**：自动管理请求生命周期，防止内存泄漏。
        - **内存与CPU优化**：智能的缓存和图片采样策略，有效避免OOM。
        - **易用性高**：链式调用，一行代码完成大多数加载需求。
    - **不足**：
        - **包体积**：会略微增加APK大小，但带来的稳定性和效率提升是值得的。
    - **挑战与解决**：
        - **挑战**：加载用户上传的身份证、人脸识别等大图或敏感图片。
        - **解决思路**：配置Glide的磁盘缓存策略，并对敏感图片在加载后于内存中进行清理。可考虑对图片进行加密存储，加载时解密。

### web端

1. 核心框架：Vue 3 + JavaScript
   - **选择原因**：Vue 3是当前主流版本，直接使用JavaScript而非TypeScript，大幅降低学习门槛和初期开发难度。
   - **优势**：
       - **学习成本低**：团队无需学习TypeScript的复杂类型系统，可以快速上手开发。
       - **开发速度快**：省略了类型定义环节，对于快速迭代和原型开发非常友好。
       - **灵活性高**：在业务逻辑复杂且变化快的场景下，不受类型约束。
   - **不足**：
       - **维护性相对较弱**：项目规模扩大后，缺乏类型提示和约束，代码可维护性会下降。
       - **调试难度**：运行时错误可能更多，且不易在开发阶段提前发现。
   **挑战与解决**：
       - **挑战**：如何在无类型约束下保证大型项目的代码质量。
       - **解决思路**：
        1.  采用 **JSDoc** 对关键函数和变量进行注释，提供基本的类型提示。
        2.  配置 **ESLint** 严格规则，统一代码风格，避免常见错误。
        3.  后期项目稳定后，可考虑渐进式迁移至TypeScript。

2. 状态管理：Pinia
   - **选择原因**：它在Vue 3生态中是Vuex的官方替代品，且API比Vuex简单得多，更易学习和使用。
   - **优势**：
       - **概念简单**：只有 `state`、`getters`、`actions` 三个核心概念，没有Vuex中繁琐的 `mutations`。
       - **TypeScript支持可选**：即使不用TS，其清晰的API也足够好用。
   - **挑战与解决**：
       - **挑战**：确定何时需要使用状态管理，避免过度设计。
       - **解决思路**：遵循一个简单原则——只有当状态需要在**多个非父子组件**间共享时，才放入Pinia。组件内部状态依然使用 `ref` 和 `reactive`。

3. 路由：Vue Router
   - **选择原因**：Vue官方路由，与Vue核心深度集成，文档和社区资源最丰富，遇到问题容易找到解决方案。
   - **优势**：
       - **开箱即用**：配置简单，基础功能无需额外学习。
       - **导航守卫直观**：通过 `beforeEach` 等函数实现权限控制，逻辑清晰。
   - **挑战与解决**：
       - **挑战**：实现页面权限控制。
       - **解决思路**：在全局路由守卫中判断用户登录状态和权限，决定是跳转到目标页还是登录页。

4. 请求库：Axios
   - **选择原因**：目前最流行、最稳定的HTTP客户端，API简单直观，文档齐全。
   - **优势**：
       - **Promise-based**：使用 `.then` 和 `.catch` 或 `async/await` 处理异步，符合现代编程习惯。
       - **拦截器强大**：可以统一处理添加Token、报错提示等，非常方便。
   - **不足**：
       需要简单的封装才能发挥最大效用。
   - **挑战与解决**：
       - **挑战**：统一处理错误和加载状态。
       - **解决思路**：创建一个 `request.js` 文件，在里面创建Axios实例并配置拦截器。所有请求都通过这个实例发出，从而实现统一管理。

5. 构建工具：Vite
   - **选择原因**：Vue官方推荐的构建工具，相比传统的Webpack，启动速度和热更新速度极快，能极大提升开发幸福感。
   - **优势**：
        - **极速启动**：秒级启动开发服务器。
        - **配置简单**：开箱即用，对Vue支持最好。
   - **不足**：
       生态插件的丰富度略低于Webpack，但对于大部分项目足够。
   - **挑战与解决**：
       - **挑战**：一些老旧库或特殊配置可能在Vite中需要适配。
       - **解决思路**：Vite社区活跃，大部分常见问题都能找到解决方案。其官方插件也覆盖了大部分Vue项目所需功能。

## UI

1. XML布局 + ViewBinding（UI构建方案）
    - **Java生态深度契合**：XML布局与Java代码完美配合，通过ViewBinding生成类型安全的视图引用，避免传统findViewById的类型转换风险，与Java语言特性高度匹配
    - **Android Studio工具链优化**：IDE对XML布局提供实时预览、可视化拖拽编辑和Lint检查，与Java编译链无缝集成，支持联合调试
    - **稳定性**:基于Android原生View系统，编译时直接转换为平台代码，在各类设备上渲染性能稳定可靠

2. RecyclerView + 自定义Adapter（风控数据列表）
    - **大数据集高效处理**:针对风控系统海量借贷申请、信用记录等数据，通过ViewHolder复用机制确保列表滚动流畅，内存占用可控
    - **风险等级可视化**:可根据信用评分、风险等级等业务数据动态调整项样式，如通过不同颜色标识高风险（红色）、中风险（黄色）、低风险（绿色）客户
    - **与Java业务逻辑紧密集成**:Adapter数据绑定逻辑可用纯Java实现，与后端Spring Boot业务规则保持一致性
    - **动画反馈业务状态**:支持项增删动画，当风控审批状态变更时提供视觉反馈，增强操作体验

3. Material Design Components（金融级UI组件）
    - **企业级设计规范**:提供符合金融应用标准的组件库，如Data Table展示风控指标、Bottom Sheets显示详细风控规则，确保界面专业严谨
    - **主题系统统一管理**:通过MaterialTheme统一配置品牌色和字体，与后端Java系统的设计语言保持一致
    - **表单验证强化**:TextInputLayout提供完善的错误提示和验证状态，确保风控数据录入的准确性
    - **无障碍访问支持**:内置符合WCAG标准的无障碍功能，满足金融行业合规要求

4. Fragment + Navigation（页面导航架构）
    - **业务流程模块化**:将贷前审核、风险评估、贷后监控等环节封装为独立Fragment，实现功能解耦和代码复用
    - **与Java业务对象协同**:ragment arguments支持Parcelable Java对象传递，完整保持风控数据模型一致性
    - **状态持久化**:FragmentManager提供状态保存和恢复，确保用户在不同页面间的操作状态不丢失

5. MPAndroidChart + 自定义渲染（风控数据可视化）
    - **金融图表专业展示**提供折线图展示信用趋势、柱状图对比风险指标、饼图显示资产分布，满足风控分析多样化需求
    - **实时数据更新**：结合LiveData可实现风控指标的实时监控和图表动态更新
    - **交互式数据分析**:可通过手势缩放、拖拽等交互方式查看数据，提升分析效率和准确性




## 后端

1. java
    - **跨平台性**：“一次编写，到处运行”特性使其部署灵活
    - **高性能与稳定性**：JVM 经过多年优化，具备优秀的性能表现和内存管理能力，适合构建高并发、长时间运行的后端服务
    - **强大的生态系统**：拥有大量成熟的库、框架和工具（如 Maven、Gradle、JUnit、Log4j 等）
    - **企业级支持**：广泛用于金融、电信、电商等对稳定性要求高的行业

2. Spring(Spring Boot)
    - **依赖注入（IoC）与面向切面（AOP）**：这是Spring的核心。IoC让代码结构更清晰、更易于管理和测试（松耦合）。AOP可以优雅地解决跨领域问题，如日志、事务、安全等，而无需侵入业务代码。
    - **快速开发**：Spring Boot通过自动配置和 Starter 依赖，极大地减少了XML和样板代码的编写。如只需要引入一个spring-boot-starter-web，就自动配置好了Tomcat和一个基础的Web环境
    - **全面的技术集成**：Spring项目为几乎所有主流技术都提供了无缝集成方案，包括但不限于
        - 数据访问：Spring Data JPA (用于ORM)， Spring Data JDBC, MyBatis集成
        - 安全：Spring Security，功能极其强大的安全框架
        - 消息队列：对Kafka， RabbitMQ等的良好支持
        - 云原生：Spring Cloud为微服务架构提供了一整套解决方案
    - **强大的事务管理**：提供了声明式事务管理，用简单的注解（@Transactional）就能管理复杂的事务，非常方便可靠

3. MySQL
    - **开源免费**：MySQL 是最流行的开源关系型数据库之一，成本低
    - **成熟稳定**：经过数十年发展，事务支持（ACID）、主从复制、备份恢复等机制非常成熟
    - **性能良好**：对于大多数 Web 应用（如用户管理、订单系统、内容管理），MySQL 足够高效
    - **生态兼容性好**：与 Java/Spring 集成无缝（通过 JDBC、MyBatis、JPA/Hibernate 等）
    - **云原生支持**：各大云厂商（阿里云、AWS、腾讯云）都提供托管 MySQL 服务

4. Redis
    - **极高读写性能**：基于内存操作，QPS 可达 10w+，适合缓存热点数据（如用户会话、商品信息）
    - **丰富数据结构**：支持 String、Hash、List、Set、ZSet 等，可用于实现排行榜、限流、分布式锁等场景
    - **持久化与高可用**：支持 RDB/AOF 持久化，以及主从复制、哨兵、集群模式，保障数据安全和系统可用性
    - **减轻数据库压力**：将频繁读取的数据缓存到 Redis，显著降低 MySQL 负载
    - **与Spring集成良好**：通过 Spring Data Redis 可轻松操作 Redis

## 安卓用户信息获取

### 手机终端信息:

#### **高价值、相对稳定的信息（强标识性）**

这些信息变化频率低，是构建设备指纹的核心。

| 终端信息 | 说明 | 为何能作为“本人”标志 |
| :--- | :--- | :--- |
| **设备唯一标识符** | - `Android ID`<br>- `OAID` (匿名设备标识符，推荐用于合规场景)<br>- `GAID` (Google Advertising ID，可重置)<br>- `IMEI`/`MEID` (需特殊权限，且在安卓10+受限，不推荐直接采集) | 这些是设备的“身份证号”。如果一个账户长期只在某个`OAID`或`Android ID`的设备上登录，那么该设备再次登录时，系统会认为“很可能是本人”。 |
| **设备型号与品牌** | `Build.MODEL`, `Build.BRAND` (如 `Xiaomi 13`, `iPhone 15 Pro`) | 用户通常长期使用同一型号设备。突然从“iPhone”切换到“华为”高端机，可能需要额外验证。 |
| **操作系统版本** | `Build.VERSION.SDK_INT`, `Build.VERSION.RELEASE` (如 Android 14, HarmonyOS 4.0) | 操作系统版本升级较慢，短期内稳定。 |
| **硬件信息** | - CPU型号/核心数<br>- RAM大小<br>- 屏幕分辨率<br>- 传感器列表 | 硬件组合具有唯一性，可辅助区分设备。 |
| **SIM卡信息** | `IMSI` (国际移动用户识别码，需权限且敏感)、运营商名称 | 如果用户长期使用同一张SIM卡，可作为辅助判断。但双卡手机和换卡情况常见。 |

####  **中等价值、可变但有规律的信息（行为+设备）**

这些信息结合使用，能增强识别的准确性。

| 终端信息 | 说明 | 为何能作为“本人”标志 |
| :--- | :--- | :--- |
| **网络环境** | - IP地址及地理位置<br>- 连接的Wi-Fi SSID (如 `home_wifi`, `company_5G`)<br>- 网络类型 (4G/5G/Wi-Fi) | 用户常在固定地点（家、公司）登录。突然出现在异地IP或陌生Wi-Fi，风险升高。 |
| **应用安装列表** | 设备上已安装的应用包名列表 (需权限) | 每个用户的App组合是独特的。如果设备上装有该账户常用App（如银行、邮箱），则可信度高。 |
| **设备设置** | 语言、时区、亮度、字体大小等 | 用户习惯稳定，突然变更可能异常。 |

### 用户习惯方面:

#### **1. 设备操作行为 (Device Interaction Patterns)**

| 习惯类型 | 说明 | 可验证性 |
| :--- | :--- | :--- |
| **打字节奏 (Keystroke Dynamics)** | 用户的打字速度、按键时长、相邻按键的间隔时间、滑动输入的轨迹速度等。 | **高**。每个人打字的“节奏感”不同，是研究最成熟的行为特征之一。 |
| **触摸屏手势 (Touchscreen Gestures)** | 滑动的速度、加速度、轨迹的平滑度、点击屏幕的力度（如果设备支持）、双指缩放的惯用手等。 |  **中高**。手势模式具有个人特色。 |
| **设备握持与移动 (Device Handling)** | 通过陀螺仪和加速度计检测用户手持设备的姿势、行走时的晃动模式、设备倾斜角度等。 |  **中**。不同用户的步态和持机习惯不同。 |

#### **2. 应用使用模式 (Application Usage Patterns)**

| 习惯类型 | 说明 | 可验证性 |
| :--- | :--- | :--- |
| **使用时间与频率 (Usage Timing & Frequency)** | 用户通常在什么时间段使用App（如每天早上8点查邮件，晚上9点刷视频），使用某个功能的频率。 |  **中低**。易受生活变化影响，需结合其他特征。 |
| **功能导航路径 (Navigation Path)** | 用户在App内的操作路径，例如总是从首页点击A按钮，再进入B页面，最后执行C操作。 |  **中**。熟练用户有固定的“工作流”。 |
| **常用功能与设置 (Preferred Features & Settings)** | 用户偏好的设置（如语言、主题、通知开关）、常使用的功能模块。 |  **低**。容易改变，不适合作为主要验证依据。 |

#### **3. 位置与移动模式 (Location & Mobility Patterns)**

| 习惯类型 | 说明 | 可验证性 |
| :--- | :--- | :--- |
| **常去地点 (Frequent Locations)** | 用户经常出现的地点，如家、公司、常去的健身房。 |  **中高**。结合时间规律，能构建独特的“生活圈”。 |
| **出行方式 (Travel Mode)** | 通过传感器和位置数据判断用户是步行、骑车、开车还是乘坐公共交通。 |  **中**。不同用户的通勤方式稳定。 |

#### **4. 交互与内容偏好 (Interaction & Content Preferences)**

| 习惯类型 | 说明 | 可验证性 |
| :--- | :--- | :--- |
| **交互风格 (Interaction Style)** | 用户是喜欢快速滑动浏览，还是仔细阅读每一条内容；是频繁点赞，还是很少互动。 |  **低**。主观性强，变化大。 |
| **内容偏好 (Content Affinity)** | 用户长期关注的领域、阅读的文章类型、观看的视频类别。 |  **低**。偏好会随时间改变，不适合作为身份验证依据。 |
