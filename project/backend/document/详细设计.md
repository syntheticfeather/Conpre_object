# 详细设计

## Redis 分布式锁（AOP + Redisson）

### 设计目标

- 以注解方式在方法级别声明分布式锁，避免业务代码显式编写 tryLock/unlock 模板代码
- 支持通过 SpEL 动态拼装锁 Key，实现“按业务主键粒度加锁”
- 支持可配置的等待时间、持有时间（leaseTime）以及失败策略（返回 null 或抛业务异常）

### 相关实现与依赖

- 注解：[RedisLocked.java](../personal-loan/src/main/java/com/example/personal_loan/aop/RedisLocked.java)
- 切面：[RedisLockAspect.java](../personal-loan/src/main/java/com/example/personal_loan/aop/RedisLockAspect.java)
- RedissonClient：由 redisson-spring-boot-starter 提供并注入；配置见 [application.yml](../personal-loan/src/main/resources/application.yml#L23-L48)
- 业务异常：[BusinessException.java](../personal-loan/src/main/java/com/example/personal_loan/exception/BusinessException.java) 与 [GlobalExceptionHandler.java](../personal-loan/src/main/java/com/example/personal_loan/handler/GlobalExceptionHandler.java)

### 注解设计（RedisLocked）

- key：锁键，支持 SpEL 表达式；表达式求值结果为 null 会抛出 BusinessException(400, "锁key为空")
- waitTime：等待锁超时时间；默认 0 表示不等待，直接 tryLock() 一次
- leaseTime：锁持有时间；默认 -1 表示使用看门狗机制（自动续期）
- timeUnit：waitTime/leaseTime 的时间单位；默认秒
- failCode：获取锁失败时的业务错误码；默认 423（锁冲突）
- failMessage：获取锁失败时的错误信息；默认“获取锁失败”
- returnNullOnFail：获取锁失败时是否直接返回 null；默认 false（抛异常）

### 切面流程（RedisLockAspect）

#### 1. 拦截点

- 使用 @Around("@annotation(redisLocked)") 拦截所有标记了 @RedisLocked 的方法

#### 2. 锁 Key 解析（SpEL）

实现位置：RedisLockAspect.evaluateLockKey

- 支持两类变量来源：
  - 按参数名注入：#userId、#applicationId 等（依赖编译时参数名保留；若无法获取参数名则此类变量不可用）
  - 按下标注入：#p0/#p1... 或 #a0/#a1...（始终可用）
- 表达式解析后结果为 null 直接抛 BusinessException(400, "锁key为空")，阻止业务继续执行

示例（设计建议）：

```java
@RedisLocked(key = "'lock:application:withdraw:' + #applicationId")
public void withdrawApplication(Long userId, Long applicationId) { ... }
```

#### 3. 获取锁（tryAcquire）

实现位置：RedisLockAspect.tryAcquire

- leaseTime > 0：
  - 调用 lock.tryLock(waitTime, leaseTime, unit)
  - 行为：可等待 waitTime；拿到锁后最多持有 leaseTime；不会启用看门狗续期
- waitTime > 0 且 leaseTime <= 0：
  - 调用 lock.tryLock(waitTime, unit)
  - 行为：可等待 waitTime；持有时间走 Redisson 默认与看门狗机制（由 lockWatchdogTimeout 控制）
- waitTime == 0 且 leaseTime <= 0：
  - 调用 lock.tryLock()
  - 行为：不等待，抢不到立即失败；持有时间走 Redisson 默认与看门狗机制

#### 4. 失败处理策略

获取锁失败后有两种策略：

- returnNullOnFail = true：直接返回 null（更适合“无副作用读操作/可接受空结果”的场景）
- returnNullOnFail = false：抛出 BusinessException(failCode, failMessage)

注意：当前全局异常处理对 BusinessException 的 HTTP 状态码映射为：

- code == 404：HTTP 404
- 其他 code：HTTP 400

因此注解默认的 failCode=423 并不会在 HTTP 层体现为 423（仍会以 HTTP 400 返回，但响应体中的 code 字段为 423）。

#### 5. 执行业务与释放锁

- 成功加锁后执行 joinPoint.proceed() 进入原始业务方法
- finally 块中释放锁：
  - 先判断 lock.isHeldByCurrentThread()，防止释放他人锁
  - unlock 时捕获 IllegalMonitorStateException 并忽略（例如锁已过期被 Redis 删除）

### 注意事项与已知问题

- 锁粒度：锁 Key 必须包含业务前缀与业务主键，避免不同业务误用同一锁
- 参数名 SpEL：若运行环境无法获取参数名，建议使用 #p0/#a0 等下标变量保证表达式可用
- 切面顺序：RedisLockAspect 期望通过 @Order(1) 保证优先于事务切面，但当前导入的是 org.junit.jupiter.api.Order，无法对 Spring AOP 的切面顺序生效

## 消息机制（RabbitMQ + Outbox + 幂等 + 重试/DLQ）

### 设计目标

- 业务与消息投递解耦：业务事务内只写本地消息表，不直接依赖 MQ 可用性
- 生产者可确认：仅在 Broker confirm ack 后将 outbox 标记为 SENT
- 消费者可控：手动 ACK，确保“处理完成才确认”，支持重试与 DLQ
- 关键业务可审计：messageId/txId/业务键可追踪，避免丢单与重复副作用

### 关键实现

#### 1) Outbox Pattern（本地消息表）

- 表结构：outbox_message（状态 PENDING/SENDING/SENT/FAILED）
  - DDL：[V1.0_create_table.sql](../personal-loan/db-init/V1.0_create_table.sql#L145-L158)
  - 实体：[OutboxMessage.java](../personal-loan/src/main/java/com/example/personal_loan/entity/OutboxMessage.java)
  - Mapper：[OutboxMapper.java](../personal-loan/src/main/java/com/example/personal_loan/mapper/OutboxMapper.java)

- 写入时机：业务事务内写入 outbox_message（例如还款发起写 payment.requested）
  - 还款入口：[OrderServiceImpl.repay](../personal-loan/src/main/java/com/example/personal_loan/service/impl/OrderServiceImpl.java#L63-L96)

#### 2) Outbox 轮询投递与 SENDING 超时回滚

- 轮询器：按批次拉取 PENDING，先更新为 SENDING，再投递 MQ
  - 实现：[OutboxMessagePoller.java](../personal-loan/src/main/java/com/example/personal_loan/mq/OutboxMessagePoller.java)
- 超时回滚：定时将长期处于 SENDING 的消息回滚为 PENDING，避免发送进程崩溃导致消息“卡死”
  - Mapper 方法：resetExpiredSendingToPending
  - 轮询器定时任务：rollbackExpiredSending

#### 3) 生产者确认（Publisher Confirm/Returns）

- 配置：开启 publisher-confirm-type=correlated、publisher-returns=true、mandatory=true
  - 配置文件：[application.yml](../personal-loan/src/main/resources/application.yml#L49-L79)
- 发送方式：发送时携带 CorrelationData(messageId)，并将 messageId 写入 header，用于 returns 回调定位消息
  - 发送工具：[RabbitUtil.java](../personal-loan/src/main/java/com/example/personal_loan/utils/RabbitUtil.java)
- 回调落库：
  - ConfirmCallback：ack=true -> outbox SENT；ack=false -> outbox FAILED
  - ReturnsCallback：路由失败 -> outbox FAILED
  - 实现：[RabbitTemplateConfig.java](../personal-loan/src/main/java/com/example/personal_loan/config/RabbitTemplateConfig.java)

#### 4) 消费者确认（Manual ACK）与幂等

- 全局手动 ACK：listener.simple.acknowledge-mode=manual
- 幂等表：processed_message（messageId 主键）
  - DDL：[V1.0_create_table.sql](../personal-loan/db-init/V1.0_create_table.sql#L160-L165)
  - Mapper：[ProcessMessageMapper.java](../personal-loan/src/main/java/com/example/personal_loan/mapper/ProcessMessageMapper.java)
- ACK 策略：
  - 幂等命中：直接 ACK
  - 业务成功 + 幂等记录写入成功：ACK
  - 失败：按重试次数进入重试队列或 DLQ

#### 5) 重试与死信（Retry Queue + DLQ）

- 重试队列：TTL + DLX 回流到主 exchange，实现延迟重试
- DLQ：超过最大重试次数，或不可恢复的错误，转入 DLQ
- 配置：主队列绑定 DLX；重试队列绑定 DLX 并设置 TTL
  - 示例（loan application）：[RabbitMQConfig.java](../personal-loan/src/main/java/com/example/personal_loan/config/RabbitMQConfig.java)
- 重试计数：基于消息 headers 的 x-death（按 queue 聚合 count）判断是否超过阈值

### 支付/还款事件流（职责拆分）

#### 事件模型

- payment.requested：表示“支付已发起/待支付执行”
  - DTO：[PaymentRequestedEvent.java](../personal-loan/src/main/java/com/example/personal_loan/dto/PaymentRequestedEvent.java)

- payment.success：表示“支付网关确认成功”
  - DTO：[PaymentSuccessEvent.java](../personal-loan/src/main/java/com/example/personal_loan/dto/PaymentSuccessEvent.java)
  - txId：支付网关返回的交易流水号/支付订单号（第三方唯一标识），用于幂等与对账，目前模拟为`"mock_tx_" + request.getOrderId() + "_" + System.currentTimeMillis()`

- order.repaid：表示“订单域入账完成（还款一期/状态更新完成）”，供通知等下游消费

#### 执行链路

- repay 接口：仅计算应还金额并写入`payment.requested`和`Outbox`，不直接入账
  - [OrderServiceImpl.repay](../personal-loan/src/main/java/com/example/personal_loan/service/impl/OrderServiceImpl.java#L63-L96)

- payment.success 消费入账：先写支付记录表做 txId 幂等，再更新订单并发布 order.repaid Outbox
  - [PaymentSuccessConsumer.java](../personal-loan/src/main/java/com/example/personal_loan/mq/PaymentSuccessConsumer.java)

- order.repaid 通知消费：对通知类副作用做幂等与可重试处理
  - [OrderRepaidConsumer.java](../personal-loan/src/main/java/com/example/personal_loan/mq/OrderRepaidConsumer.java)

### 支付记录表（payment_record）

- 表结构：payment_record，tx_id UNIQUE，按 txId 做支付回调幂等
  - DDL：[V1.0_create_table.sql](../personal-loan/db-init/V1.0_create_table.sql#L160-L172)

- Mapper：插入时若触发 DuplicateKeyException，说明 txId 已处理，直接 ACK
  - [PaymentRecordMapper.java](../personal-loan/src/main/java/com/example/personal_loan/mapper/PaymentRecordMapper.java)

## 站内通知与 SSE（贷款申请状态变更）

### 设计目标

- 对用户隐藏内部审核分支（例如 AI拒绝进入人工复核），仅展示 4 类对外状态
- 申请提交/审核操作不被通知逻辑阻塞，通知链路异步化
- 通知可追踪、可重试、可隔离（毒消息进入 DLQ）

### 事件与路由

- 通知事件 DTO：`NotificationEvent`
  - [NotificationEvent.java](../personal-loan/src/main/java/com/example/personal_loan/dto/NotificationEvent.java)
- Routing key：`notification.loan-application`
  - 配置常量：`RabbitMQConfig.NOTIFICATION_ROUTING_KEY`
  - [RabbitMQConfig.java](../personal-loan/src/main/java/com/example/personal_loan/config/RabbitMQConfig.java)
- 队列：
  - 主队列：`notification.queue`
  - 重试队列：`notification.retry.queue`（TTL + DLX 回流）
  - 超限隔离：DLQ（复用 dead-letter exchange + 死信队列）

### 端到端流程

#### 1) 业务侧产生命令（状态变更）

- 提交申请：写申请记录后，写 outbox（loan.application.submitted）触发 AI 审批；同时写 outbox（notification.loan-application）触发用户“审核中”通知
- AI 通过：更新申请为已通过并创建订单，同时写 outbox（notification.loan-application）触发用户“已通过”通知
- 人工审核：通过/拒绝后更新申请并创建订单（通过时），同时写 outbox（notification.loan-application）触发用户“已通过/申请失败”通知
- 撤回申请：状态更新为已取消，同时写 outbox（notification.loan-application）触发用户“已取消”通知

通知 outbox 写入由 `NotificationOutboxPublisher` 统一封装：

- [NotificationOutboxPublisher.java](../personal-loan/src/main/java/com/example/personal_loan/mq/NotificationOutboxPublisher.java)

#### 2) Outbox 投递到 MQ（可靠投递）

轮询器按批次拉取 PENDING，抢占为 SENDING 后投递到 exchange，并携带 `messageId` header 用于幂等：

- [OutboxMessagePoller.java](../personal-loan/src/main/java/com/example/personal_loan/mq/OutboxMessagePoller.java)
- outbox 表：`outbox_message`
  - [V1.0__create_table.sql](../personal-loan/db-init/V1.0__create_table.sql#L145-L160)

#### 3) 通知消费与副作用（落库 + SSE）

消费者使用手动 ACK，确保“落库成功 + 幂等记录写入成功”后才 ACK。失败时依据 x-death 次数重试，超限后转入 DLQ 隔离。

- 消费者：[NotificationConsumer.java](../personal-loan/src/main/java/com/example/personal_loan/mq/NotificationConsumer.java)
- 幂等表：`processed_message`（message_id 主键）
  - [V1.0__create_table.sql](../personal-loan/db-init/V1.0__create_table.sql#L173-L179)

通知落库：

- 表：`notifications`
  - [V1.0__create_table.sql](../personal-loan/db-init/V1.0__create_table.sql#L181-L193)
- Mapper：[NotificationMapper.java](../personal-loan/src/main/java/com/example/personal_loan/mapper/NotificationMapper.java)

SSE 推送：

- `NotificationConsumer` 在落库后调用 `NotificationSseService.publish(userId, notification)` 将通知实时推送给在线用户
- SSE 管理实现：[NotificationSseServiceImpl.java](../personal-loan/src/main/java/com/example/personal_loan/service/impl/NotificationSseServiceImpl.java)

### API 设计

- `GET /api/notifications/my?limit=20`：获取我的通知列表（用于离线查询/补拉）
- `PATCH /api/notifications/{notificationId}/read`：标记已读
- `GET /api/notifications/stream`：SSE 订阅实时通知流
  - Controller：[NotificationController.java](../personal-loan/src/main/java/com/example/personal_loan/controller/NotificationController.java)

### 对外状态映射

用户侧状态由业务侧在写通知事件时决定，保持稳定口径：

- 审核中 / 已通过 / 申请失败 / 已取消

内部状态 `AI拒绝` 仅用于人工审核队列，不作为用户侧“失败”展示，也不触发用户侧失败通知。
