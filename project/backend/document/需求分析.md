# 需求分析

## 分布式锁（Redis/Redisson）

### 背景与目标

系统存在并发访问同一业务资源的场景（例如同一笔申请/订单被重复提交、重复撤回、重复扣减/释放额度、同一条数据被并发更新）。为避免“重复执行导致的数据不一致/脏写”，需要在关键业务入口提供分布式互斥能力。

基于 Redisson 的方法级分布式锁能力（以 AOP + 注解形式提供），用于将“加锁/解锁”从业务代码中抽离，减少重复代码，统一失败策略。

### 适用范围（典型场景）

- 防止重复提交/重复点击：对“状态变更型接口”进行互斥（撤回申请、提交申请、审核操作等）
- 并发写保护：同一业务主键（如 applicationId、orderId、userId）维度的并发写入互斥
- 幂等与互斥配合：在需要“只允许同一业务键串行执行”的操作中使用（与 MQ 幂等表等方案互补）

### 功能性需求

- 支持在方法上声明式加锁：通过注解指定锁 Key（支持 SpEL 表达式）
- 支持配置等待时间与持有时间：可选择“不等待立即失败”或“等待一段时间”
- 支持失败策略可配置：失败时可选择返回 null 或抛出业务异常
- 锁必须在方法执行结束后释放：无论成功或抛异常，都需要确保释放

### 约束与非功能性需求

- 锁 Key 需要具备业务唯一性与明确的前缀规范，避免不同业务误共用同一把锁
- 锁持有时间（leaseTime）需要覆盖业务逻辑最坏执行时间；若使用看门狗机制，应确保线程不会被长时间阻塞导致续期失效
- 获取锁失败属于“并发冲突/资源争用”，需要有一致的对外响应与可观测性（错误码/错误信息）

## 消息机制（RabbitMQ + Outbox + 幂等 + 重试/DLQ）

### 背景与目标

系统存在“关键业务状态变化 + 异步处理/通知”的场景，例如：

- 贷款申请提交后触发 AI 审批与订单创建
- 用户还款后触发入账、通知与对账

这类链路的核心风险是“消息丢失/重复/乱序”导致的业务一致性问题（丢单、重复入账、重复通知）。因此需要建立一套可靠消息机制，目标是：

- 保证消息不丢：业务落库与消息发送具备一致性
- 支持消息重试：可自动重试、可转入 DLQ，支持人工补偿
- 关键业务不丢单：订单创建、还款入账场景具备幂等与可追踪性

### 功能性需求

- 生产者可靠投递
  - 支持 Publisher Confirm，确认消息已被 Broker 接收并持久化后才视为“发送成功”
  - 支持 Publisher Returns，路由失败可回调并落库标记，避免静默丢弃
- 本地消息表（Outbox Pattern）
  - 在业务事务内写入 outbox_message，后台异步投递到 MQ
  - outbox 具备状态（PENDING/SENDING/SENT/FAILED），支持重试与超时回滚
- 消费者可靠消费
  - 使用手动 ACK，确保“业务处理成功 + 幂等记录写入成功”后才 ACK
  - 幂等命中直接 ACK，避免重复投递导致消息积压
- 重试与死信
  - 支持重试队列（TTL + DLX 回流）实现延迟重试
  - 支持 DLQ 收敛不可恢复的消息，便于人工排查与补偿
- 支付入账职责拆分（还款场景）
  - repay 入口仅发起支付请求（payment.requested），不直接入账
  - 支付成功（payment.success）触发入账并发布订单域事件（order.repaid）
  - 引入支付记录表 payment_record，txId unique 用于幂等、对账与追踪

### 约束与非功能性需求

- 可观测性：消息需具备 messageId（链路追踪）、业务键（orderId/applicationId）与错误原因落库/日志
- 幂等优先：允许“至少一次投递”，通过幂等消除重复副作用
- 可补偿：DLQ 消息可重放或人工补偿，不影响主链路吞吐
