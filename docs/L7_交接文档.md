## 3. 概念速查（不熟的话先看这里）

| 概念 | 一句话解释 |
|---|---|
| **VLM** | 视觉语言模型，能看图并输出文字；这里负责把材料图片转成 Markdown |
| **LLM** | 文本大模型；这里负责把材料文本抽成 12 维风险特征 JSON |
| **token** | 模型计费单位；输入、输出分别计费 |
| **prompt** | 给模型的指令 + 数据；本项目 system prompt 稳定，user prompt 放申请数据 |
| **前缀缓存** | 推理引擎缓存相同输入前缀；只省输入 token，不缓存答案 |
| **特征值缓存** | 我们自己的缓存：相同材料+上下文 → 直接复用特征 JSON，省掉整个 LLM 调用 |
| **`.md` 缓存** | VLM 转录结果缓存；源文件 hash 不变就不重转 |
| **feature schema** | 特征列表、顺序、版本；训练和推理必须完全一致 |
| **full 模型** | 一个 XGBoost，输入 = 结构化特征 + G 组 + H 组 |
| **baseline / +LLM / +full** | 离线消融实验的三组特征，不是线上三个模型 |
| **MQ** | 消息队列；生产者和消费者解耦 |
| **exchange / queue / routing key** | RabbitMQ 的路由概念；先按现有代码风格配置即可 |
| **Outbox** | 在同一个数据库事务里写一条“待发送消息”，再由后台投递，避免消息丢失 |
| **ACK** | 消费者确认消息处理成功；失败不 ACK，消息会重投 |
| **DLQ** | 死信队列；重试多次仍失败的消息进这里，避免无限重试 |
| **幂等** | 同一条消息/请求处理多次，结果只生效一次；用唯一键实现 |
| **状态机** | 任务只允许按 `QUEUED → CONVERTING → ...` 迁移 |
| **`risk_job`** | 风控任务表；记录状态、阶段、分数、特征、版本 |
| **SSE** | Server-Sent Events；服务端主动推送通知给在线用户 |
| **PII** | 个人身份信息，如身份证、手机号、银行卡 |
| **feature flag** | 配置开关；新链路出问题可以一键关掉，回退旧逻辑 |

## 4. L7.1 同步闭环（第 1 周，必须完成）

### 4.1 目标

不搞 MQ，先把业务链路接通：

```text
Java 提交申请
  → 组装请求
  → POST /v1/risk/features
  → 拿 G/H 特征
  → 合并 full 向量
  → full XGBoost
  → 写 risk_job
  → 更新申请状态
```

### 4.2 接口契约

`POST /v1/risk/features`，请求头 `X-API-Key`。

请求：

```json
{
  "application_id": 1001,
  "application": {"amount": 50000, "term": 12, "income": 8000},
  "documents": [
    {"type": "salary_cert", "source_path": "1001/01_salary_cert.png"},
    {"type": "credit_report", "text": "征信报告：..."}
  ],
  "application_note": "客户申请装修贷"
}
```

响应：

```json
{
  "application_id": 1001,
  "status": "ok",
  "error_code": null,
  "features": {"llm_verdict": 1, "llm_confidence": 0.86, "...": "..."},
  "deterministic_features": {"doc_count": 5, "...": "..."},
  "document_conversion": [
    {"type": "salary_cert", "status": "ready", "cached": false}
  ],
  "reasoning": "...",
  "model": "deepseek-flash",
  "cached": false
}
```

失败时 `status="error"`，但 `features` 仍然存在（全 0 + `llm_feature_available=0`），不要处理 `null`。

### 4.3 Java 要改什么

#### ① 新增 `RiskFeatureClient`

- 用 `RestTemplate` 或 `WebClient`；
- 读配置：`risk.service.url`、`risk.service.api-key`、`risk.service.timeout-ms`；
- 请求头 `X-API-Key`；
- 超时/401/5xx 抛出明确异常，由上层降级；
- 不要在日志里打印材料原文或 API Key。

#### ② 新增请求组装器

从现有代码拿数据：

- 结构化特征：`MlTrainingLogService.extractModelFeatures(...)`（9 维）或 `collectFeatures` 的 58 维；
- 材料路径：`work_cert`、`tri_cert`、`immovables_cert`；
- 申请上下文：`loan_applications` 的金额、期限、收入。

注意：`source_path` 是相对于 `RISK_DOC_BASE_DIR` 的路径，不是绝对路径。

#### ③ 统一 feature schema（最重要）

现在有三套维度：

| 位置 | 维度 |
|---|---|
| Java 线上 `RiskScoringServiceImpl` | 9 |
| `feature_config.py` | 54 |
| `MlTrainingLogServiceImpl.collectFeatures` | 约 58 |

**必须先和组长确认用哪一套**。建议：

- 定义一个共享的 `feature_schema`（字段列表 + 顺序 + 版本号）；
- Java 和 Python 都用它；
- full 模型训练和推理使用同一版本；
- 模型文件、schema 版本、prompt 版本一起发布。

#### ④ 结果表

建议直接用 `risk_job`（L7.2 也用它，避免再建一张表）：

```sql
CREATE TABLE risk_job (
  job_id BIGINT PRIMARY KEY AUTO_INCREMENT,
  application_id BIGINT NOT NULL,
  user_id BIGINT NOT NULL,
  job_version INT NOT NULL DEFAULT 1,
  status VARCHAR(20) NOT NULL,
  stage VARCHAR(20),
  attempt INT NOT NULL DEFAULT 0,
  error_code VARCHAR(50),
  score DECIMAL(6,5),
  features_json JSON,
  feature_set VARCHAR(20) DEFAULT 'full',
  model_version VARCHAR(50),
  prompt_version VARCHAR(50),
  converter_version VARCHAR(50),
  document_count INT DEFAULT 0,
  converted_count INT DEFAULT 0,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  started_at DATETIME,
  finished_at DATETIME,
  updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uk_app_version (application_id, job_version),
  KEY idx_status_updated (status, updated_at)
);
```

L7.1 同步版可以只写一条 `status='COMPLETED'` 的记录。

#### ⑤ 接入申请流程

在 `ApplicationServiceImpl` 里：

- 用 feature flag 控制新链路；
- 先跑旧逻辑作为兜底；
- 新链路失败时不要回滚申请，标记降级并继续；
- 不要在 LLM 特征没到之前自动放款。

#### ⑥ 失败降级

```text
Python 超时 / 401 / 5xx / 坏 JSON
  → G 组默认值 + llm_feature_available=0
  → 仍然进同一个 full XGBoost
  → 得到降级分
  → 金额/风险阈值决定正常走还是转人工
```

### 4.4 Python 侧要改什么

大概率不用改代码，只需要配置：

```dotenv
RISK_API_KEY=...
RISK_DOC_BASE_DIR=./uploads
RISK_REQUEST_TIMEOUT=30
RISK_FEATURE_CACHE_PATH=.cache/risk_features.json
```

启动：

```bash
cd ml-risk-model
python -m uvicorn llm_features.api.app:app --host 127.0.0.1 --port 8000
```

### 4.5 L7.1 验收用例

| 用例 | 预期 |
|---|---|
| 正常申请 | Java 拿到特征，写 `risk_job`，状态更新 |
| Python 超时 | 申请不失败，降级分/转人工 |
| API Key 错误 | 降级，日志有清晰错误 |
| 材料路径错误 | `INVALID_PATH`，降级 |
| 特征 schema 不匹配 | 启动时或测试时直接报错 |
| 相同申请重复提交 | 幂等，不重复写结果 |

### 4.6 L7.1 常见坑

- 9 维模型吃 58 维特征 → 分数完全错；
- 特征顺序和训练时不一致 → 分数错；
- XGBoost4j 加载的模型文件不是 full 模型；
- 把 `source_path` 当绝对路径传给 Python；
- Python 超时后 Java 线程池被占满；
- 在 LLM 特征没到之前自动通过。

## 5. L7.2 异步骨架（第 2 周，尽量完成）

### 5.1 目标

先跑通 Mock 链路，不接真实 VLM/LLM：

```text
提交申请
  → 写 loan_application + risk_job + Outbox
  → 返回“计算中”
  → MQ(risk.job.created)
  → Python Mock Worker
  → MQ(risk.job.completed)
  → Java Consumer
  → 更新状态 + SSE 通知
```

### 5.2 状态机

```text
QUEUED → CONVERTING → EXTRACTING → SCORING → COMPLETED
                                      ↘ FAILED → MANUAL_REVIEW
```

L7.2 骨架可以先只实现：

```text
QUEUED → PROCESSING → COMPLETED / FAILED
```

再逐步细化。

### 5.3 MQ 设计

| 项 | 建议 |
|---|---|
| Exchange | `risk.exchange`（topic） |
| 创建事件 | `risk.job.created` |
| 完成事件 | `risk.job.completed` |
| 失败事件 | `risk.job.failed` |
| 死信 | `risk.dlq` |
| 消息内容 | 只放 ID 和版本，不放材料原文/PII |

消息示例：

```json
{"event":"RISK_JOB_CREATED","job_id":"uuid","application_id":123,"user_id":45,"job_version":1,"attempt":0}
```

```json
{"event":"RISK_JOB_COMPLETED","job_id":"uuid","application_id":123,"status":"ok","score":0.18,"features":{...},"model_version":"...","prompt_version":"..."}
```

### 5.4 Python Mock Worker

- 消费 `risk.job.created`；
- 用 Mock VLM/LLM 或直接返回固定特征；
- 发布 `risk.job.completed`；
- 先不要接真实 VLM/LLM，先把消息链路跑通。

### 5.5 Java Consumer

- 消费 `risk.job.completed`；
- 更新 `risk_job` 和 `loan_application`；
- 写通知（复用 `NotificationOutboxPublisher`）；
- 通过 `NotificationSseService` 推送；
- 离线用户下次登录能看到通知列表。

通知类型建议：

- 新类型 `RISK_RESULT_READY`；
- 如果前端不方便改，先复用 `LOAN_APPLICATION_STATUS`。

### 5.6 幂等、重试、DLQ

| 问题 | 做法 |
|---|---|
| 消息重复 | `(application_id, job_version)` 唯一键；Worker 先查状态 |
| Worker 崩溃 | 手动 ACK；未 ACK 会重投 |
| 重试 | 指数退避，最多 3 次 |
| 失败 | 进 DLQ，状态 `FAILED/MANUAL_REVIEW` |
| 通知丢失 | Outbox + 通知表；SSE 只是推送通道 |

### 5.7 L7.2 验收用例

| 用例 | 预期 |
|---|---|
| 提交申请 | 立即返回“计算中”，有 `job_id` |
| Worker 成功 | `risk_job.COMPLETED`，SSE 收到通知 |
| 重复消息 | 只处理一次，分数不重复写 |
| Worker 失败 | `FAILED`，转人工，通知用户 |
| 通知离线 | 登录后通知列表能看到 |
| 队列积压 | 有日志/指标可观察 |

### 5.8 如果时间不够，砍什么

按顺序砍：

1. 真实 VLM/LLM（保留 Mock）；
2. 多进程并行（先单进程）；
3. DLQ 和复杂重试（先记录失败）；
4. SSE（先写通知表，用户登录能看到）；
5. L7.2 整体延后，优先保证 L7.1 质量。

## 10. 常见坑（务必看）

1. **9 维 vs 58 维**：不要拿 9 维模型直接吃 58 维特征。
2. **特征顺序**：XGBoost 对顺序敏感，训练/推理必须一致。
3. **模型文件**：Java 加载的 `.json` 必须是 full 模型，不是旧的 9 维模型。
4. **PII 进 MQ**：消息只放 `application_id`，Worker 回库查路径。
5. **提前放款**：LLM 特征没到之前不要自动通过。
6. **重复消费**：没有幂等键，会重复写结果、重复扣费。
7. **Outbox 事务**：业务写入和 Outbox 必须在同一事务。
8. **SSE 离线**：SSE 只推在线用户，通知表才是兜底。
9. **超时**：Python 超时后 Java 线程可能仍被占用；要设合理超时和线程池。
10. **合成数据**：不要把合成数据 AUC 当业务结论。
